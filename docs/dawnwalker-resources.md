# Dawnwalker native resource restoration

Trainer **0.5.2**, package **1.0.3**, corrects the interaction between native resource locks and percent refills on Steam build **25915545 / CL-265636**. Runtime ownership remains limited to the validated local possessed living pawn and its ASC; pre-existing active game locks are not replaced.

The exact-build `SetHealthPercent` thunk **0x5FEF894** calls **0x6029860**. That implementation first remembers whether CombatComponent's health handle at **0x7C8** differs from -1, calls `UnlockHealth` if it does, restores health, then calls `LockHealth` if the remembered condition was true. It tests the numeric handle, not active-effect existence. Therefore a retained inactive ID also makes this getter/setter path create a new infinite override. `UnlockHealth` itself (**0x602D494**) removes the effect and clears the field to -1; the local remembered condition still causes re-locking afterward. `SetStaminaPercent` thunk **0x5FEFEA8** calls **0x6029CBC**, with the equivalent sequence using **0x7D0**, `UnlockStamina` **0x602D4E0** and `LockStamina` **0x60203D0**.

The previous activation path refilled before creating its owned lock. With a stale native ID this refill could create an active override first; the subsequent ownership check then rejected it as `Health ownership changed before locking`, leaving the refill-created effect untracked. This exact error was captured from the running 0.5.1 trainer. A passive snapshot found the resulting active HealthOverride, while the trainer's health flag was false. The user's separate report of a switched-on control with draining health has not been measured against the new runtime, and should not be treated as gameplay validation.

Activation now validates an absent/inactive game lock and creates an owned lock before refilling. A controlled percent refill may replace only that known active lease's handle: the old effect must be retired and its synchronous successor must have exactly one active stack. Component/ASC identity and the full resource value are rechecked, and cleanup follows the successor. An unknown outcome blocks overlapping changes and requests a restart. Replacements observed outside the trainer's own refill operation retain the existing conservative game-ownership protection.

Refill while infinite health/stamina is enabled retains the requested toggle and follows the native successor rather than first dropping the owned lease. Refill while disabled obtains a temporary owned lock, restores the resource, then releases it; it never requests enabling the toggle, even if cleanup fails. Native health/stamina handles are read through pinned aliases and never assigned directly. There is no save edit, resurrection or guarantee against scripted death.

Offline fixtures now model the native remembered-condition re-locking and Unlock's -1 reset. Tests cover stale IDs, repeated one-shot refills, repeated refills with the infinite toggle enabled, full-value no-ops, max-resource changes, foreign locks/effects, final successor cleanup, partial failures and changed ownership. Actual post-update resource depletion and combinations with invulnerability still need gameplay confirmation after restarting into the new trainer.
